# CipherTrader Crypto LLM 다중 에이전트 설계

## 1. 문서 목적

기존 CipherTrader Crypto의 하드코딩 중심 자동매매를 역할별 LLM 에이전트가 판단하고 거래하는 구조로 전환한다.

이 문서는 대화에서 확정한 내용을 계속 누적하는 설계 원본이다. 아직 결정하지 않은 항목은 임의로 확정하지 않고 `미결정 사항`에 기록한다.

관련 저장소:

- 공개 소개·배포 연결: `btsky99/vibe-coding`
- CipherTrader Crypto 원본: `btsky99/crypto-bot`
- 배포 파일: `btsky99/crypto-bot-releases`

## 2. 핵심 원칙

1. 기술 지표 값은 코드가 계산한다.
2. 계산된 지표와 시장 상태는 PostgreSQL에 저장한다.
3. 역할별 터미널 에이전트는 중앙 메시지 버스로 통신한다.
4. 진입 여부와 주문 구성은 LLM 진입 에이전트가 추론한다.
5. 체결된 포지션은 별도의 오픈 포지션 관리 에이전트가 담당한다.
6. 주문 실행기는 LLM의 구조화된 주문 지시를 거래소 API 요청으로 변환한다.
7. 진입 분석은 매분이 아니라 각 전략 시간봉의 봉 마감 직후 실행한다.
8. 최초 구현은 모의거래로 검증한 뒤 실거래 단계로 확장한다.

## 3. 전체 흐름

```text
거래소 시세·캔들·호가
          ↓
지표 계산 엔진
          ↓
PostgreSQL 데이터 저장
          ↓
중앙 메시지 버스
          ↓
봉 마감 이벤트
          ↓
진입 에이전트
          ↓
진입·DCA·SL·TP·금액 계획
          ↓
안전 한도 검사
          ↓
자동매매 주문 실행기
          ↓
거래소 주문 및 체결
          ↓
오픈 포지션 관리 에이전트
          ↓
유지·DCA 변경·SL 이동·부분청산·전체청산
```

## 4. 지표 계산 엔진

LLM이 원시 캔들로 모든 수치를 직접 계산하지 않는다. 재현성과 속도가 필요한 계산은 일반 코드로 수행한다.

초기 지표 범위:

- 캔들 패턴
- RSI
- MACD
- 일목균형표
- 상승·하락 다이버전스
- 지지선과 저항선
- 추세 채널
- 엘리엇 파동 후보
- 피보나치 되돌림과 확장
- 거래량
- 변동성
- 펀딩비
- 미결제약정

코드는 시장을 대신 판단하지 않고 측정값과 구조 후보를 제공한다. 엘리엇 파동처럼 해석이 여러 개 가능한 항목은 코드가 피벗과 파동 후보를 만들고 LLM이 다른 지표와 함께 최종 해석한다.

지표 결과의 기본 저장 단위:

```text
거래소 + 심볼 + 시간봉 + 봉 종료 시각 + 지표 버전
```

## 5. 분석 대상

진입 에이전트의 초기 분석 대상은 거래 가능한 코인 중 시가총액·유동성 등 선정 기준에 따른 상위 50개 코인이다.

상위 50개의 선정 기준은 아직 확정하지 않았다. 거래 불가능하거나 유동성이 부족한 코인은 대상에서 제외할 수 있어야 한다.

## 6. 전략 시간봉과 실행 시점

| 매매 유형 | 기준 시간봉 | 진입 분석 실행 |
|---|---:|---|
| 초단타 | 5분봉 | 5분봉 마감 직후 |
| 단타 | 15분봉 | 15분봉 마감 직후 |
| 데이트레이딩 | 1시간봉 | 1시간봉 마감 직후 |
| 스윙 | 4시간봉 | 4시간봉 마감 직후 |

진입 에이전트는 1분마다 전체 시장을 추론하지 않는다. 해당 전략의 봉이 마감된 후 확정된 지표를 이용한다.

여러 시간봉이 동시에 마감되는 시각에는 코인 데이터를 중복 생성하지 않고 하나의 다중 시간봉 스냅샷으로 묶는다. LLM 호출을 한 번으로 합칠지 시간봉별로 나눌지는 성능 시험 후 결정한다.

## 7. 진입 에이전트

진입 에이전트는 상위 50개 코인의 봉 마감 지표를 비교하여 실제 신규 진입 여부와 주문 계획을 결정한다.

결정 범위:

- 거래하지 않음
- 진입 코인
- 롱 또는 숏
- 매매 유형
- 판단 기준 시간봉
- 최초 진입 가격
- 최초 진입 금액
- 전체 계좌 대비 최대 투입 금액
- DCA 개수
- 각 DCA 가격과 금액
- 손절 가격
- 분할 익절 개수
- 각 익절 가격과 청산 비율
- 진입 근거
- 진입 근거 무효화 조건
- 예상 보유 시간

투입 금액은 단일 주문만 보지 않고 다음 계좌 상태를 함께 고려한다.

- 총 계좌 평가금액
- 사용 가능한 잔액과 증거금
- 이미 열린 포지션의 총 노출
- 기존 DCA 예약금
- 기존 손절 도달 시 예상 손실
- 동일 방향 또는 상관관계가 높은 코인의 중복 노출

진입 에이전트 출력 계약 예시:

```json
{
  "symbol": "BTCUSDT",
  "strategy_type": "DAY",
  "timeframe": "1h",
  "side": "LONG",
  "initial_entry": {
    "price": 68100,
    "amount_usdt": 200
  },
  "dca_orders": [
    {"price": 67400, "amount_usdt": 150},
    {"price": 66700, "amount_usdt": 150}
  ],
  "stop_loss": 65900,
  "take_profits": [
    {"price": 69400, "close_pct": 30},
    {"price": 70700, "close_pct": 30},
    {"price": 72500, "close_pct": 40}
  ],
  "total_max_amount": 500,
  "reason": "1시간 상승 추세와 지지선 반등",
  "invalidation": "1시간봉 지지선 종가 이탈"
}
```

## 8. 안전 한도 검사

안전 한도 검사는 전략의 옳고 그름을 판단하지 않는다. LLM이 만든 주문이 계좌의 절대 제한을 위반하는지만 검사한다.

- 계좌 대비 최대 손실
- 최대 레버리지
- 하루 최대 손실
- 최대 총 노출
- 최소 주문 수량과 가격 단위
- 잘못된 가격 또는 수량
- 시세 지연과 거래소 연결 이상
- 손절 없는 신규 주문

한도 안의 전략 판단과 주문 구성은 LLM의 결정을 유지한다.

## 9. 자동매매 주문 실행기

주문 실행기는 LLM의 구조화된 출력을 거래소 주문으로 변환한다.

담당 범위:

- 최초 진입 주문 전송
- DCA 예약 주문 전송
- 거래소 측 SL 주문 등록
- 여러 단계의 TP 주문 등록
- 주문 접수·거절·부분체결·전체체결 확인
- 거래소 주문 ID와 내부 주문 ID 연결
- 주문 상태를 중앙 버스에 전달
- 실패한 주문의 재시도 가능 여부 판단

주문이 실제 체결되면 중앙 버스에 `position.opened` 이벤트를 발행하고 해당 포지션의 관리 책임을 오픈 포지션 관리 에이전트로 넘긴다.

## 10. 오픈 포지션 관리 에이전트

진입 에이전트와 포지션 관리 에이전트는 별도의 역할과 별도의 터미널 세션으로 운영한다.

관리 에이전트는 열린 포지션의 최신 지표, 최초 진입 논리, 체결 내역과 현재 손익을 계속 비교한다.

결정 범위:

- 포지션 유지
- DCA 주문 유지
- DCA 주문 취소 또는 변경
- 추가 DCA 제안
- SL 이동
- 본절 보호
- TP 가격 또는 청산 비율 변경
- 부분청산
- 전체청산
- 최초 진입 근거의 유지 또는 무효화 판정

진입 분석은 봉 마감 기준으로 실행하지만 오픈 포지션 관리는 더 빠른 주기가 필요할 수 있다. 초기 후보는 1분 주기와 중요 시장 이벤트 발생 시 즉시 실행하는 방식이다.

LLM이 응답하지 않는 순간에도 계좌가 보호되도록 기본 SL은 거래소에 등록한다.

## 11. 중앙 메시지 버스

기존 Vibe Coding에서 구상한 PostgreSQL 기반 에이전트 통신 구조를 우선 재사용한다.

핵심 이벤트 후보:

| 이벤트 | 발행자 | 주요 구독자 |
|---|---|---|
| `candle.closed` | 시장 데이터 수집기 | 지표 계산 엔진 |
| `indicators.updated` | 지표 계산 엔진 | 진입·포지션 관리 에이전트 |
| `entry.proposed` | 진입 에이전트 | 안전 한도 검사 |
| `entry.approved` | 안전 한도 검사 | 주문 실행기 |
| `entry.rejected` | 안전 한도 검사 | 진입 에이전트·TUI |
| `order.submitted` | 주문 실행기 | TUI·감사 로그 |
| `order.filled` | 주문 실행기 | 포지션 저장소 |
| `position.opened` | 포지션 저장소 | 포지션 관리 에이전트 |
| `position.updated` | 포지션 관리 에이전트 | 주문 실행기·TUI |
| `position.closed` | 주문 실행기 | 복기 에이전트 |
| `agent.warning` | 모든 에이전트 | 감독 에이전트·TUI |

모든 이벤트는 최소한 다음 값을 가진다.

- 이벤트 ID
- 이벤트 종류
- 발생 시각
- 발행 에이전트
- 거래소
- 심볼
- 포지션 또는 주문 ID
- 상관관계 ID
- 구조화된 데이터
- 처리 상태

## 12. TUI 초기 화면

터미널 UI는 역할별 상태를 동시에 확인할 수 있게 구성한다.

```text
┌ 시장·봉 마감 상태 ────────┬ 진입 에이전트 ────────────┐
│ 상위 50개·지표 갱신       │ 후보·근거·주문 계획       │
├ 오픈 포지션 ──────────────┼ 포지션 관리 에이전트 ─────┤
│ 손익·DCA·SL·TP·노출       │ 유지·변경·청산 판단       │
├ 중앙 버스 ────────────────┼ 주문 실행기 ──────────────┤
│ 이벤트·에이전트 메시지    │ 제출·체결·거절·오류       │
└ 계좌 상태·안전 한도·모의/실거래 모드 ────────────────┘
```

## 13. 초기 구현 단계

1. 기존 CipherTrader Crypto 코드와 DB 구조 분석
2. 지표 계산 결과의 공통 스키마 정의
3. 중앙 메시지 버스 이벤트 계약 정의
4. 읽기 전용 TUI 구축
5. 봉 마감 스케줄러 구축
6. 진입 에이전트의 구조화된 출력 구현
7. 모의 주문 실행기 연결
8. 오픈 포지션 관리 에이전트 구현
9. 거래 복기와 에이전트 판단 기록
10. 모의거래 장기 시험
11. 문제 수정 후 제한된 실거래 시험

## 14. 미결정 사항

- 상위 50개 코인의 정확한 선정 기준
- 지원할 첫 거래소
- 현물·선물 지원 범위
- 포지션 관리 에이전트의 기본 실행 주기
- 동시 최대 오픈 포지션 수
- 시간봉별로 동일 LLM을 사용할지 별도 에이전트를 둘지
- 진입 LLM과 관리 LLM의 공급자 및 모델
- Claude Max 구독형 CLI의 실제 24시간 처리량
- TUI 구현 언어와 프레임워크
- 모의거래 체결·슬리피지 모델
- 뉴스·거시경제 에이전트 추가 시점
- 거래 복기 에이전트의 메모리 승격 규칙
