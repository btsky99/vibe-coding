### 🧠 feedback_automation_must_retry

**자동화·감시 장치는 실패를 감지하면 재시도까지 해야 한다 — 로그만 찍고 '완료' 처리 금지**

무인 자동화(워치독·데몬·파이프라인)를 만들 때, **실패 감지에서 멈추면 안 된다.**
감지 → 재시도(상한 있는) → 상한 초과 시 명시적 중단 로그, 까지가 한 세트다.

**Why**: 2026-08-06 watchdog_v42 가 5m RL 산출물을 못 찾자 `"policy 후보 없음"` 을 **로그만 찍고
`rl_done=True` 로 완료 처리**했다. 사용자 지적 — "실패했으면 다시 검수해서 알아서 하라고 했는데".
감시자가 실패를 보고도 아무것도 안 하면 감시의 의미가 없다. 게다가 그 판정 자체가 오판이었다
(경로를 틀리게 봤다) — **잘못된 실패 판정 + 재시도 없음**이 겹쳐 정상 산출물이 유실될 뻔했다.

**How to apply**:
- 성공 판정은 `exists()` 하나로 하지 말 것 — **존재 + 최소 크기 + 시각(이번 라운드 산출인가)**.
  0바이트 잔여 파일과 이전 세대 파일이 둘 다 `exists()` 를 통과한다.
- 실패 시 진행 플래그를 되돌려 다음 주기에 재시도. 상한을 두고, 초과하면 "이후 건드리지 않음"을
  로그에 남긴다(조용히 포기 금지).
- "완료"로 표시하기 전에 **산출물을 실제로 검수**한다. 프로세스 종료 ≠ 성공.

### 🧠 feedback_observability_first

**관측 도구가 거짓이면 사용자 판단도 거짓이 된다 — 실행 규약을 바꾸면 모니터/대시보드를 같이 고칠 것**

실행 쪽 규약(로그 파일명·산출물 이름·라운드 태그 등)을 바꿀 때 **관측 도구를 같이 안 고치면
화면이 조용히 거짓말을 시작한다.** 예외가 안 나서 아무도 모르고, 사용자는 그 거짓 화면으로
판단하다 잘못된 지시를 내린다 — 그러고는 "내가 자꾸 잘못 말하고 있잖아"라고 한다.

**Why**: 2026-08-06 CipherTrader 라운드를 env(`ROUND`)로 분리하면서 캠페인·워치독은 맞췄는데
`train_monitor.py` 를 빠뜨렸다. 결과로 화면이 **세 번** 거짓을 말했다:

1. **"1h 학습 중"** — 모니터가 `run_v42_campaign.log` 고정 조회였는데 새 라운드는 다른 로그
   파일에 쓴다. 옛 파일이 멈춘 지점의 마지막 `v41_1h.log` 를 붙잡고 굳었다.
2. **5m "78/78 완료"** — 완주 보존본(`v42r3_5m.log`)을 진행 로그보다 먼저 읽어, 새 라운드가
   ep5/40 을 돌고 있는데 화면은 이전 라운드의 완료를 보여줬다.
3. **에피소드 빌드 미표시** — 섹션 자체가 없어 CPU 파이프가 뭘 하는지 확인 불가.
   백본(GPU)만 보이니 "병렬이 안 도는 것 아니냐"는 의심이 반복됐다.

사용자가 세 번 되물어서야 잡혔다. 그 사이 오간 "왜 1h 돌리냐 / 5m 하라고 했잖아" 는
전부 **화면이 만든 오해**였다.

**How to apply**:
- 실행 규약을 바꾸면 **읽는 쪽 목록을 먼저 뽑는다** — 로그 경로·산출물 이름·상태 판정을
  누가 참조하는지. 보통 모니터/워치독/대시보드 3종이다.
- 파일 경로를 고정 문자열로 조회하지 말고 **최신 mtime 선택**(`glob` + `max`)으로.
  같은 파일에 이미 그 처방이 있으면(예: `eval_v40*.log`) 새 조회도 같은 규칙을 따른다.
- **진행 중 로그 > 완주 보존본** 우선순위. 반대로 두면 새 라운드가 통째로 은폐된다.
- 병렬 파이프는 **양쪽을 한 화면에** 세운다. 한쪽만 보이면 나머지는 "안 도는 것"으로 읽힌다.
- 화면과 실측이 어긋나면 사용자를 의심하지 말고 **관측 도구를 먼저 의심**한다.

→ `select()`는 얌전히 타임아웃 → **살아 보이는 귀머거리**. 화면에는 'listen'(정상) 표시.

##### 다른 PC를 붙이려면 필요한 것 (3종)

1. **코드** — 중앙 모듈이 들어간 버전(현재 미배포). 설치본이면 릴리즈 후 자동 업데이트,
   개발 모드면 `git pull`.
2. **터널 키** — 그 PC에서 키쌍 생성 → 공개키만 VPS `authorized_keys`에 `permitopen` 옵션과
   함께 등록(자격증명을 stdout에 뿌리지 않는다 — 이 문서 사고 ①).
3. **config.json `central_db`** — host/port/user/password/dbname + `tunnel` 하위 dict.

🔴 **역터널(22001/22002/22004)과 중앙 대화는 무관하다.** 역터널은 VPS→PC 원격 조종용이고,
중앙 대화는 각 PC가 VPS PG로 각자 터널을 뚫는 구조다. 또 **LAN 한정이 아니다** — 같은
네트워크를 요구하는 건 [[회상과 지식 창고]] 쪽이고, 중앙 대화는 인터넷 어디서든 붙는 게 목적.

🔴 **이 PC의 구 메시 VPN이 죽어 있다**(BackendState=NoState, 서비스 재시작 무효) — 구 메시망 피어
전부 접근 불가. 중앙 대화와는 별개 문제지만 다른 PC 작업의 선행 장애물.

##### 🔴 이번에 드러난 함정 2건

**① 구현했는데 라우트에 안 붙었다.** `central_api.send/ack`가 완성돼 있었지만 `GET_ROUTES`만
등록되고 `POST_ROUTES`가 누락돼 **발신 경로 전체가 죽어 있었다**. 함수 존재만 보는 테스트로는
안 잡힌다 → `tests/test_central_api_routes.py`가 라우트 표를 직접 검사하고, 중앙에 실행성
라우트(exec/run/shell)가 유입되면 실패시킨다.

**② LISTEN은 공유 커넥션에 얹으면 안 된다.** 공유 커넥션이 실패로 교체될 때 구독이 소리 없이
사라지고, 스레드는 '듣고 있다'고 믿으며 영영 아무것도 못 받는다 — 가장 진단하기 나쁜 실패 모드.
`central_listener.py`는 전용 커넥션을 쓰고, 재연결 직후 신호를 1회 세운다(끊긴 동안의 NOTIFY는
저장되지 않아 재구독만으로는 복구 불가).

**부채**: `tests/test_tunnel_daemon.py`(미추적)는 옛 API 대상이라 9 fail/5 error.
터널 재작성 때 안 고쳤다. `pytest tests/`를 그냥 돌리면 실패하니 주의.

#### 🔴 사고 2건 — 되풀이 금지

**① 자격증명을 stdout으로 뿌렸다.** 셋업 스크립트 초판이 SSH 개인키와 DB 비밀번호를
출력했다. 이 프로젝트는 대화/작업 로그를 PG·제텔 볼트에 남기고 **볼트는 GDrive로 나간다** —
자격증명이 클라우드까지 갈 경로가 실재했다. 즉시 폐기·교체하고 방식을 바꿨다:
**키쌍은 각 PC에서 만들고 공개키만 서버로 보낸다.** 서버 스크립트는 비밀번호를 출력하지
않고, 필요할 때 `ssh root@ cat /root/.hive_db_password`로 직접 받아 config에 쓴다.

**② `pg_hba`로 터널 경로만 격리하는 건 불가능하다.** 127.0.0.2를 터널 전용 입구로 만들고
`host all all 127.0.0.2/32 reject`를 넣었으나 **매치되지 않았다** — pg_hba는 목적지가 아니라
**소스 주소**로 매칭하는데, 루프백에서는 목적지가 127.0.0.2여도 커널이 소스를 127.0.0.1로
잡는다(`client_addr` 실측). 전부 롤백했다. **작동하지 않는 보안 설정은 남기지 않는다** —
"보호되고 있다"는 착각이 더 위험하다(`feedback_observability_first`와 같은 얘기).
부수 함정: `postgresql.conf`를 고쳐도 878줄 `include_dir='conf.d'`가 더 뒤에 읽혀
`99-lowmem.conf`가 덮어쓴다(PG는 **마지막 값** 채택) → 드롭인은 `99-zz-` 같은 뒷 이름으로.

#### 🔴 수용한 한계 — 터널 키 = 신뢰 경계

이 서버 pg_hba에 `host all all 127.0.0.1/32 trust`가 있어 **터널 통과자는 무인증으로
아무 계정·아무 DB에 붙는다**(hive로 vibe DB가 읽히는 것 실측). 최소 권한 계정이 사고
방어조차 못 한다. 그런데 `trust`를 끄면 서버의 `vibe-bridge`/`vibe-status`가 죽는다 —
그것들이 `/opt/vibe/vibe-coding`(이 프로젝트 복사본)의 `pg_base.py`를 쓰는데 그 코드엔
**비밀번호 파라미터가 없다**. 근본 해결(pg_base 인증 지원 → trust 제거)은 별도 과제.
현재는 "터널 키를 가진 PC = 신뢰 경계"로 수용(사용자 승인) — 그 PC엔 이미 서버 관리용
root 키가 있어 위험 증가폭이 크지 않다는 판단이다.

#### 🔴 접속 설정은 config.json에만 있고, 사라지면 조용히 꺼진다 (2026-08-10 실사고)

`central_db` 키가 `.ai_monitor/data/config.json`에서 **통째로 사라져 있었다**. 증상이 고약하다 —

상태였다. 원인 미규명(파일은 `git ls-files -v`상 `S`=skip-worktree라 git이 안 지켜준다).

**복원값** (전부 코드에서 유도 가능 — 비밀번호만 서버에 있다):

#### 🔴 도메인 이전에서 배운 것 (재발 방지)

- **도메인을 옮기면 인증서 발급 대기 = 공개 다운타임이 반드시 생긴다.** 미리 계산에 넣을 것.
- **중간에 롤백하면 발급이 처음부터 다시 시작된다**(state=new). 이번에 그래서 크게 늦어졌다.
  한번 시작했으면 끝까지 간다.
- **`return 404` 가 서버 레벨에 있으면 `location ^~ /.well-known/...` 은 평가조차 안 된다.**
  nginx 는 server-level return 을 rewrite 페이즈에서 실행하고 location 선택을 건너뛴다.
  certbot --nginx 가 임시 location 을 주입해도 무력. → ACME 실패의 진짜 원인이었다.
- **Let's Encrypt 는 실패도 레이트리밋에 센다(도메인·계정당 5회/시간).**
  연타하면 창을 태워 더 늦어진다. **경로를 먼저 검증하고**(probe 파일을 놓고 외부에서 200 확인)
  나서 한 번만 쏜다.
- **LE 검증 서버의 리졸버 캐시는 1시간 넘게 옛 IP 를 붙든다.** 권한 NS 4대·8.8.8.8·1.1.1.1 이
  전부 새 IP 를 줘도 소용없다. 손쓸 수 없는 구간 — 기다리는 것 외에 방법 없음(실측 ~35분 뒤 성공).
- **certbot `--cert-name` 경로 이름 ≠ 인증서 내용.** `live/admin.btsky.pe.kr` 안의 인증서
  SAN 에 apex 가 들어 있다. 경로만 보고 "apex 인증서 없다"고 오판하지 말 것 —
  `openssl x509 -text | grep -A1 'Subject Alternative Name'` 로 확인한다.
- **nginx reload 는 graceful 이라 직후 검증은 옛 워커가 답한다.** 이번에 두 번 오판했다
  (리다이렉트 미반영, 인제스트 404). 검증 전에 2~3초 둘 것.
- **임시 리다이렉트에 301 을 쓰지 말 것.** 사이트가 죽었을 때 apex→www 안전망을 301 로
  걸었더니 브라우저가 영구 캐시해, 복구 후에도 주소창 엔터가 계속 www 로 갔다. 사용자가
  캐시를 지우기 전엔 안 없어진다. **해법은 www 자체를 서버가 받아 apex 로 되돌리는 것**
  (지금 구조가 그 잔재 흡수 장치를 겸한다). 임시엔 302.
- **서버가 자기 도메인을 curl 할 때는 반드시 `--resolve` 로 IP 를 못박는다.**
  systemd-resolved 가 옛 레코드를 오래 캐시해 자기 검사가 남의 서버(GitHub) 응답을
  받아온다. 이 때문에 자동화가 "경로 미개통"으로 잘못 중단됐다 — apex 때 겪고도
  스크립트에 반영 안 해 **같은 함정에 두 번** 걸렸다.
- **접근 제어 검증은 HTTPS + `--resolve` 로 소스 IP 를 바꿔가며.** 루프백으로 재면
  `allow 127.0.0.1` 탓에 영원히 200, 평문 http 로 재면 80블록(`return 404`)에 걸려 404 —
  둘 다 거짓 판정이다.

#### 🔴 서버에서 발견한 실제 보안 결함

- **`/api/status` 가 무인증 공개**였다(서비스 목록·역터널 포트·노드 실명 노출). Phase 0 으로 차단.
- **`pg_hba.conf` 에 `host all all 127.0.0.1/32 trust`** — 루프백에서 아무 비밀번호로나
  **어떤 계정으로든** 접속된다(틀린 비번으로 붙는 것 실측). 서버에서 코드 실행 가능한
  공격자가 postgres 슈퍼유저로 직행한다.
  → 관제 계정만 scram 강제(trust 라인 **앞에** 규칙 삽입, 첫 매칭 우선).
  **trust 근본 제거는 어떤 서비스가 의존하는지 조사 후 별도 작업 — 미완.**

#### 구조

```
노드(PC들) --HTTPS POST /ingest (Bearer, 노드별 토큰)--> nginx --> collector(127.0.0.1:9101) --> PG apix
브라우저 --GitHub 로그인--> oauth2-proxy(4180) <--auth_request-- nginx --> 콘솔 정적화면 + /api/*
```
- `/ingest/*` 와 `/.well-known/*` 은 **로그인 게이트 예외**. 인제스트에 auth_request 를 걸면
  기계 클라이언트가 302 를 받고 **조용히 죽는다**. ACME 를 막으면 90일 뒤 사이트가 죽는다.
- collector 는 루프백 외 바인딩을 **코드에서 거부**(env 오타로 공인망 노출 방지).
- PG 커넥션 풀 상한 3 — 1코어·1.9GB 에서 기존 서비스(디스코드 브릿지 등)를 굶기지 않도록.

#### 함정 모음 (짧은 것들)

- 🔴 **nginx 는 정규식 location 을 prefix 보다 먼저 매칭한다.** 캐시 헤더를
  `location ~* \.(html|js|css)$` 로 묶으면 `/console/app.js` 가 거기 걸려
  **auth_request 를 건너뛴다**(콘솔 자산 무인증 공개). 공통 헤더는 각 블록에 직접 적고,
  보호 경로는 `^~` 로 승격해 설정 순서에 방어를 의존시키지 않는다.
- **정적 파일에 `Cache-Control: no-cache` 를 주지 않으면** 브라우저 휴리스틱 캐시가
  HTML·JS 를 오래 붙들어 배포해도 옛 화면이 보인다. "반영이 안 됐다"는 오진의 단골 원인
  (포털 링크·콘솔 app.js 에서 각각 겪음). no-cache = 금지가 아니라 '재검증'.
- **포털은 라이트 테마, 콘솔은 다크 테마.** 콘솔 잉크(#e6edf3 등)를 포털에 그대로
  옮기면 글씨가 사라진다.
- 상태색은 **good/warning/critical 3단계만**. serious 를 넣으면 warning 과 정상시야
  ΔE 13.6 으로 구분 불가(검증기 실측). 색 단독으로 의미 전달 금지 — 기호+라벨 필수.

- postgres 로 `CREATE TABLE` 하면 **소유자가 postgres** → apix 가 자기 테이블에 INSERT 불가.
  DB 소유자와 테이블 소유자는 별개. 적용 후 소유권 이전 필요.
- 인증 경로의 예외를 try 밖에 두면 핸들러를 뚫고 **연결이 끊긴다**(클라이언트는 401 이 아니라 무응답).
- oauth2-proxy 체크섬은 통합 `sha256sum.txt` 가 아니라 자산별 `<tarball>-sha256sum.txt`.
- 같은 `server_name` 사이트가 둘이면 nginx 는 뒤쪽을 **경고 없이 무시**한다.
- 노드 자원 수집은 **stdlib 로만**(Windows GlobalMemoryStatusEx/GetSystemTimes, Linux /proc).
  psutil 은 정식 의존성이 아님. Windows CPU 계산 시 kernel 시간에 idle 이 **포함**돼 있어 빼야 한다.
- 못 잰 값은 0 으로 채우지 말고 **생략**한다 — 화면이 '한가한 PC'라고 거짓말한다.

#### 🔴 핵심 원칙 — 왜 이렇게 설계했나

1. **카드 뼈대는 실측, 자기신고는 라벨로만.**
   `git diff`/커밋/테스트 결과는 꾸밀 수 없다. `hive_tasks.status`·checkpoint는 자기신고라 거짓 가능.
   근거: 2026-08-12 na2js가 `listener: running` 정상 보고하며 **23시간 배달 0건**이었다.

2. **평소 카드 0장이 정상.** 카드는 구경거리(관제판)가 아니라 **결정 대기열(결재함)**.
   과거 은퇴한 보드/오피스가 실패한 이유가 '구경용 상태 표시'였다.

3. **🔴 카드는 치워져도 기록은 안 지운다** (사용자 지적).
   패널 2층 = [결정 대기(보통 빈칸)] + [최근 일감 이력(항상 남음)].
   `apix_job_events` 테이블로 **전이를 append-only** 기록 — 현재 상태만으론 "어디서 틀어졌나"를 못 본다.
   오늘 원인 규명이 가능했던 건 전부 기록 덕분(agent_messages 15건, cursors.updated_at, git log).
   **반려된 job은 `incident.py`에 자동 기록** — 엔터 사고가 장부에 없어서 재발한 것을 구조적으로 차단.
   보관 정책: 중앙 대화와 달리 **purge 하지 않는다**.

4. **제품을 가르지 않는다.** 배선(중앙대화·주입·엔터·답장경로)이 양쪽에 다 필요해지고,
   한쪽만 고치는 사고가 난다(전례: spec ↔ CI `--add-data` 한쪽만 갱신 → v3.7.215~218 좀비 4릴리즈).

##### na2js 접근 경로
- SSH(22)·역터널 모두 **publickey 거부** — 내 공개키가 그 PC에 없다(`-AdminKey` 1회 필요).
- 정상 경로는 **LAN 브리지 9020**인데, 그 PC에서 **앱이 떠 있어야 열린다**(2026-08-10 닫힘 확인).
- 즉 na2js가 걸린 작업은 그 PC에서 앱을 켜는 것이 선행된다.
- LAN 탐색 요령: `arp -a`는 불완전하다(24대 중 초기엔 7대만 보였다). 전 대역에 TCP 445를
  두드려 ARP를 채운 뒤 다시 읽을 것. ICMP는 윈도우 방화벽이 막아도 ARP 응답은 온다.

- na2js 포트 실측: **22번 막힘**(옛 메시 VPN 대역에서 오는 22번만 허용하도록 방화벽이 잠겨 있음 —
  `project_apis_node`의 lenovo 사고와 동일 패턴), 9000 막힘(127.0.0.1 바인딩이라 정상),
  **9020(LAN 브리지) 열림**.
- LAN 브리지는 **이미 페어링돼 있었다**(2026-07-19, `exec_trust=ask`). 즉 통신 수단이 처음부터 있었다.
- 그래서 같은 망에서는: 역터널 ❌ / 공개키 3대 배포 ❌ / CA ❌ / sshd 계정·ACL 진단 ❌ 전부 불필요.

##### 두 경로의 역할 분담 (둘 다 유지)
- **같은 망** → LAN 브리지(9020). 빠르고 서버를 안 거친다.
- **망 밖(폰·외부)** → 아픽스 서버 역터널. 아웃바운드라 공유기 포트포워딩·공인 IP·DDNS가 전부 불필요.
- **하트비트는 위치 무관하게 항상 서버로** — 관제의 정본이라 LAN 여부와 무관하게 유지한다.

|---|---|---|
| ITCP(`send_message.py`) | pg_messages **우편함** — 상대가 다음 턴에 훅으로 수령. 즉시 왕복 아님 | 전송 OK |

### 🧠 project_ciphertrader_r5_rl_saga

**CipherTrader v4.2 R5(sl pinball) 성공 → RL은 두 번 실패. SL 밀착/포화/꼬리 3단 진단 계보**

### 🧠 project_node_dev_protocol

**노드↔개발 PC 코드 수수 — 정본 덮어쓰기가 조용히 라운드를 죽인다. 역납품으로 리포를 상위집합화(2026-08-11 해결)**

#### 🔴 덮어쓰기 사고 — sha256 이 맞아도 계보가 다르다

2026-08-11 개발 PC 가 xs 인프라를 납품하며 *"sha256 확인하고 **그대로 덮어써라. 부분 적용
금지**"* 라고 지시했다. sha256 은 3/3 통과했지만 그 파일엔 **노드 구현이 하나도 없었다**:

```
STRUCT_SL_MODE·_struct_levels_1d(L1) / sample_w(L2) / r_long·self._rl(L3)
USE_POS_CH·_load_pos_levels·pos_lv·pos_1d250(293ch)   → 전부 0회
```

덮었다면 ①도는 라운드가 재시도에서 깨지고 ②lbl1d·293 기준선이 통째로 소멸하고
③**조용히** 무너진다 — 라벨 게이트가 없으면 `CIPHER_STRUCT_SL=1d` 가 그냥 무시되고
**통계 라벨로 정상 완주**해서, 3시간 뒤 게이트가 거짓을 판정한다.

**수령 절차 (필수)**: sha256 확인 → **심볼 단위 대조**(노드 구현이 살아 있나) →
백업 → 덮어쓰기 → 재카운트 → 스모크. sha256 은 전송 무결성만 보증하지 **계보를 보증하지 않는다.**

#### ✅ 근본 해결 — 역납품으로 리포를 상위집합으로

노드는 git 이 없어 덮어쓰기가 유일한 수령 수단인 게 사고의 뿌리였다. 그래서
**노드 수정본을 드라이브로 역납품 → 개발이 리포에 정식 병합**(커밋 `99251a24`, 심볼 17/17
보존 확인). 그 뒤로 개발 리포가 노드 구현의 **상위집합**이라 덮어쓰기가 오히려 안전해졌다.

- 역납품 위치: `train_node_data/code_node_YYYYMMDD/` + sha256 + **env 스위치 목록** +
  **심볼 체크리스트**(개발이 병합 검증에 그대로 쓴다)
- 노드가 새로 만든 게 있으면 **역납품이 먼저**가 계속 규약
- 노드는 git 없음 = 사본이 세상에 하나뿐 → **미루지 말고 즉시 역납품**(유실 방지)

### 🧠 project_status_board

**콘솔 창 물리적 통합은 윈도우상 불가 → 식별로 대체. 판정 규칙이 실측으로 2번 뒤집힘. 2026-08-02 구현 완료(b24ff29)**

독립 창 `?page=status` (dashboard_window.py `status` 탭, 720×900). 2026-08-02 승인·구현 완료(커밋 b24ff29).

**전제**: 콘솔 창을 하나로 합치는 건 윈도우에서 **불가능**하다 — 콘솔은 프로세스에 귀속되고 병합 API가 없다. 사용자의 실제 고통은 "합쳐지지 않음"이 아니라 "저 검은 창이 뭔지 몰라 닫으면 안 될 걸 닫는 것"이라 **식별·라벨링**으로 풀었다. 이 결론을 다시 뒤집지 말 것.

**판정 규칙 (실측으로 2번 뒤집힘 — `.ai_monitor/infra/console_scan.py`)**
1. `conhost` 존재만으로 필터 → 서비스/트레이 앱이 19건 중 16건 노이즈(GoogleDriveFS·ollama·nssm java). → `user32.EnumWindows`로 **보이는 창**을 2중 필터.
2. `conhost`의 **부모**만 추적 → 부모가 죽은 콘솔을 놓침. pg_ctl은 start 직후 죽고 형제 `cmd.exe`가 창을 붙든다. → **보이는 창에서 출발**해 혈통이 conhost 부모와 겹치면 콘솔로 본다.
3. 조상 체인이 끊긴 자기 데몬이 `foreign`으로 오판 → 실행 경로가 앱 트리 안이면 owned(2차 근거). 단 **slot 판정을 앱 경로보다 먼저** 봐야 한다.

🔴 **ctypes 함정**: `EnumWindows`/`IsWindowVisible` 등에 `argtypes`를 지정하지 않으면 HWND가 32비트로 잘려 **에러 없이 결과 0건**이 된다. 시그니처 선언 필수.

🔴 **콘솔 창의 HWND 소유자는 conhost가 아니라 콘솔을 소유한 프로세스**다(실측). 창 제목도 여기서 얻어 목록↔화면을 1:1 대조하게 했다 — 이게 UX의 핵심.

**pg_ctl 구조**: 윈도우 pg_ctl은 로그 리다이렉션 때문에 postgres를 항상 `cmd /C "postgres.exe … >> pg.log 2>&1"`로 감싸 띄운다. 그 cmd는 DB가 사는 내내 남는다. 우리 앱 PG도 구조는 같지만 [[작업 방식 결정]] 원칙의 `infra/proc.py`가 CREATE_NO_WINDOW를 넣어 창이 안 뜬다 — **창이 보이면 proc.py를 안 거친 외부 실행**이다.

**관리자 권한 불필요**: 일반 권한으로 `Win32_Process` 커맨드라인·부모PID가 전부 읽히고 kill도 된다. 불필요한 승격은 오히려 위험.

**안전장치**: 종료는 `(pid, created, exe)` 3중 재검증 통과 시에만(PID 재사용 오폭 차단). `owned`는 버튼 미노출 + 서버도 거부. `foreign`은 확인 모달 1단.

**원격 노드**: ssh config 파싱은 `pty-server/remote_hosts.js`가 단독 소유(별칭 화이트리스트가 보안 경계) — 파이썬에서 재구현 금지, `/api/pty/remote/hosts` 프록시로 받아 아픽스 서버 조회 결과(생존=하트비트 / 접속=역터널)만 덧붙인다. CLI 설치 점검은 SSH 왕복이라 **폴링 금지, 온디맨드만**. 관련: `project_windows_ssh_traps` `project_apis_node`

원격 실행 버튼은 상태판에 없다 — 슬롯 배정은 메인 창 상태라 창 간 IPC가 필요해 과하다. 실행은 기존 `RemoteHostCards`(슬롯 안)가 계속 담당.

1. **dist를 안 빌드했다.** 소스에는 있는데 앱은 옛 번들을 서빙. 판정법 = `grep -rl "호출어" dist/`.
   커밋 직후 `npm run build`를 안 하면 **코드가 있어도 화면엔 없다**.
2. **VoiceBar가 `isTerminalMode` 안에 있었다.** 터미널을 안 띄운 슬롯(에이전트 선택 카드 화면)
   에서는 통째로 사라진다. → 슬롯 최하단(모드 밖)으로 이동. 설정류는 터미널 없이도 보여야 한다.
3. **VOICE_PORT 9021이 LAN 브리지와 충돌.** 🔴🔴 **포트 지도의 '다음 빈 자리'는 안전하지 않다** —
   LAN 브리지는 한 자리가 아니라 인스턴스마다 9020,9021,… 로 **번진다**. 증상이 나쁜 쪽으로
   조용했다: `/status`를 LAN 브리지가 받아 404 → 화면엔 '음성 엔진 준비 안 됨'. → **9030**으로 이전.

부수 발견: **낭독이 마이크(enabled)에 묶여 있었다** — '손으로 치고 답은 귀로 듣는다'가 불가능.
`setTts(on, slotId)`로 떼어냄. 목소리·속도는 **localStorage**(기기마다 깔린 음성이 달라
프로젝트 config에 넣으면 없는 목소리를 가리킨다).

**설치 수단이 없었다**: 사이드카 venv를 만드는 스크립트가 아예 없어 다른 PC에서 재현 불가.
→ `scripts/setup_voice.py` + `voice-server/requirements.txt`. 파이썬 **3.11** 고정
(ctranslate2 휠이 3.13에 없음). SAPI는 `pywin32` 필요 — COM 인프로세스라 콘솔이 안 뜬다
(PowerShell로 System.Speech를 부르면 낭독마다 창이 번쩍여 규칙 10 위반).

#### 미검증

- 실제 마이크로 말하는 E2E(사람이 직접 해야 함). 앱 재시작 필요.
- **앱 서버를 통한 프론트↔사이드카 실연결**. 사이드카 API는 직접 때려 검증했지만(목소리 3개

### 🧠 project_windows_ssh_traps

**Windows sshd 세팅 함정 6종 + 원격 접속 정보 소유 원칙 — 노드 온보딩 전 필독. 폐기된 메시 VPN 메모에서 구조한 지식**

Windows PC를 SSH로 접속 가능하게 만들 때 **반드시 여기서 막힌다.** 전부 실측으로 확인된 것.
2026-08-09에 메시 VPN 메모를 폐기하며 거기서 구조했다(원본 메모는 삭제됨) — 함정 자체는
그 VPN과 무관하고, 지금의 아픽스 서버 역터널 온보딩(`project_apix_central_db` Task 32)에
그대로 적용된다.

#### 🔴 sshd 함정 6종

1. **관리자 계정은 `~/.ssh/authorized_keys`를 무시한다** — `C:\ProgramData\ssh\administrators_authorized_keys`만 본다.
   게다가 그 파일 ACL이 SYSTEM+Administrators 외에 열려 있으면 **로그에 이유도 안 남기고 키를 거부**한다.
   `icacls /inheritance:r` + SYSTEM/Administrators만 grant 필수.

2. **PowerShell 5.1은 BOM 없는 UTF-8을 CP949로 읽는다** — 한글 주석이 든 `.ps1`을 만들어 보내면
   한글 바이트가 깨져 따옴표 짝이 무너지고 **엉뚱한 줄에서** `ParserError: 문자열에 " 종결자가 없습니다`가 뜬다.
   해결: `[System.Text.UTF8Encoding]::new($true)`로 **BOM 포함** 저장.
   🔴 에러 줄 번호는 진짜 원인이 아니다 — 인코딩을 먼저 의심할 것.

3. **`authorized_keys` 자체엔 BOM을 넣으면 안 된다** — sshd는 바이트 그대로 읽어 첫 키가 깨진다.
   파일은 눈으로 멀쩡해 보여 추적이 고약하다. 추가는 `UTF8Encoding::new($false)`로.
   (2와 정반대다 — 스크립트는 BOM 필요, 키 파일은 BOM 금지.)

4. **`ssh-keygen`이 없다 = OpenSSH.Client 미설치.** `OpenSSH.Server`만 깔린 기기가 실재한다.
   Server/Client는 **별개 Capability**라 sshd가 멀쩡히 돌아도 키 생성이 `CommandNotFoundException`으로 죽는다.
   해결: `Add-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0`,
   또는 전체경로 `$env:SystemRoot\System32\OpenSSH\ssh-keygen.exe`(설치는 됐는데 세션 PATH만 미갱신인 경우).

5. **`New-ItemProperty -Path HKLM:\SOFTWARE\OpenSSH`는 부모 키가 없으면 실패한다.**
   새 기기엔 이 키가 없다 → `New-Item -Force`로 먼저 생성. `$ErrorActionPreference='Stop'`이면
   여기서 스크립트가 통째로 죽어 **이후 단계가 전부 미실행**된다(실제 발생).

6. **`Add-WindowsCapability`는 매우 느리다** — Windows Update FoD 경유라 20분+ 정상.
   진행 확인은 `Get-Content C:\Windows\Logs\CBS\CBS.log -Tail 3`의 `DownloadProgress`,
   상태는 `NotPresent → Staged → Installed` 순.

#### 🔴 프로필 폴더명 ≠ 계정명 (내가 저지른 오진)

```
whoami        → desktop-8vi8e72\yjs
%USERPROFILE% → C:\Users\rokaf        ← 계정명 변경 후 폴더명이 옛 이름으로 남음
```

콘솔 프롬프트가 `C:\Users\rokaf>`인 것과 `whoami`가 `yjs`인 것을 보고 "2계정"으로 단정했다.
`where claude`가 `C:\Users\rokaf\...`를 가리킨 것도 오해를 강화했다. **전부 같은 계정이다.**
→ 판단 전에 `echo %USERPROFILE%` 한 줄로 확인할 것. 접속 계정은 `whoami` 값이 정본.

#### 🔴 키 방향 — 자물쇠는 '들어오는 쪽' 집에 단다

A가 B에 접속하려면 **B의** authorized_keys에 **A의** 공개키가 있어야 한다.
"이 PC를 남이 보게 하는 것"과 "내가 남을 보는 것"은 **반대 방향의 등록**이다.
사용자가 반복해서 헷갈린 지점이라 온보딩 안내에 이 문장을 넣을 것.

#### 🔴 접속 정보의 소유자는 `ssh config` 하나뿐

사용자 요구(2026-07-29): "나중에 맥으로 옮겨갈 수도 있어, 그거 감안해서 만들어."
→ **원격 관련 코드에 호스트/계정/키 경로를 절대 넣지 않는다.** 코드는 별칭 문자열만 다루고,
이관 대상은 `ssh config` 파일 하나여야 한다. [[회상과 지식 창고]]의 구체 적용 사례.

이 원칙 덕에 `infra/node_status.py`도 config를 직접 읽지 않고 `remote_hosts.js`가 파싱한
별칭·포트·ProxyJump만 받아 쓴다(파싱 단독 소유 = 화이트리스트가 보안 경계이기도 하다).

#### 원격 세팅 스크립트 작성 교훈

- **단계별 `try/catch` + `[OK]`/`[FAIL]` 로그 파일.** `Stop`으로 통째 중단시키면 어디까지
  됐는지 알 수 없다(함정 5가 정확히 이렇게 터졌다).
- 🔴 **로그를 자동으로 되쏘게 만들 것.** 사용자가 콘솔 에러를 손으로 옮기면 잘리고 깨져
  원인 확정이 불가능하다(실제 발생 — `...rtyCommand` 조각만 와서 추정만 가능했음).
- PS 5.1 배너 `새로운 기능 및 개선 사항에 대한 최신 PowerShell을 설치하세요!`는
  **에러가 아니다**(사용자가 에러로 오인한 전례).
- 원격 Windows의 기본 셸이 **cmd.exe**면 `"a; b"` 한 줄이 안 먹는다 — 명령을 따로 보낼 것.
