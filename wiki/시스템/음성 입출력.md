### 🧠 project_session_recovery

**앱 비정상 종료 시 이전 작업 맥락을 자동 복구하는 active_session_context 테이블 기반 시스템**

#### 구현 완료 (2026-04-14)

앱이 튕기거나 세션이 비정상 종료되면 다음 세션 시작 시 이전 작업 맥락을 자동 브리핑하는 시스템.

##### 동작 원리
1. **UserPromptSubmit**: 매 지시마다 `active_session_context` 테이블에 현재 작업 상태 기록 (status='active')
2. **PostToolUse (Edit/Write)**: 수정 파일을 실시간으로 `modified_files` jsonb 배열에 추가
3. **Stop**: 정상 종료 시 status='done'으로 마킹
4. **다음 세션 UserPromptSubmit**: status='active'인 레코드가 있으면 중단 세션 브리핑 출력 + git diff 표시

##### 수정 파일
- `pg_store.py`: `active_session_context` 테이블 + `upsert_active_session`, `update_session_files`, `complete_active_session`, `get_interrupted_sessions` 함수
- `hive_hook.py`: UserPromptSubmit(기록+브리핑), PostToolUse(파일추가), Stop(완료마킹) 로직

**Why:** 기존 하이브 마인드는 경험 회상(키워드 유사도)만 했고, "뭘 하다가 중단됐는지"는 기록하지 않았음
**How to apply:** 앱 튕김 후 재시작 시 자동으로 브리핑 출력됨. 추가 설정 불필요.

### 🧠 project_webview_storage

**바이브 코딩 앱의 WebView2 UDF 경로 설정, private_mode 함정, 그리고 런타임 자동 업데이트로 인한 '하얀 창 + 재실행 불가' 사고**

바이브 코딩 앱의 WebView2 사용자 데이터 폴더(UDF)는
`%APPDATA%/vibe-coding/{dev|exe}/{프로젝트명}/webview_data/` 다.
`infra/app_boot.py` 의 `webview.start()` 호출부에서 `private_mode=False` + `storage_path` 로 명시 설정.
이 **한 폴더가 서로 다른 사고 2건의 무대**였다 — localStorage 유실(2026-04), 하얀 창(2026-08).

#### 사고 ① localStorage 유실 (2026-04-08, 수정 04-09)

**Why:** PyWebView 기본값 `private_mode=True` 는 시작할 때마다 `%TEMP%/tmpXXXXX/EBWebView/` 를
만들고 종료 시 지운다. 오피스 프로필 편집이 재시작마다 전부 날아갔다("저장이 안되는데").

**How to apply:**
- `webview.start()` 에서 `private_mode` 기본값에 절대 의존하지 말 것 — 명시적 False 필수
- dev/exe 를 디렉토리로 분리 — 스키마 차이로 인한 데이터 손상 방지
- "설정이 저장 안 됨" 증상의 **첫 번째 의심 대상**: 저장 경로가 tmp 로 돌아갔는지
- DevTools 가 필요하면 `webview.start(..., debug=True)`

#### 사고 ② 🔴 하얀 창 + 재실행 불가 (2026-08-15, 수정 4fde303)

증상은 "앱을 실행하면 화면이 하얗기만 하다". 그리고 **다시 실행해도 안 열린다**.

**Why:** 윈도우가 WebView2 런타임을 `151.0.4129.78 → .86` 으로 자동 업데이트했는데,
**창을 이미 잃은 옛 앱 프로세스가 UDF 를 구버전으로 점유**한 채 살아 있었다.
UDF 는 런타임 버전 하나에만 귀속되므로 새 앱이 붙으려다
`CreateCoreWebView2ControllerAsync` 에서 `0x80010108 (RPC_E_DISCONNECTED)` 로 실패.

🔴 **핵심은 실패 방식이다.** pywebview 6.1 은 이 실패를 **예외로 안 올리고 stdout 에만 찍는다**
→ 창은 뜨는데 엔진이 없어 하얀 화면. 게다가 그 프로세스가 **단일 인스턴스 락을 계속 쥐어**,
아이콘을 다시 눌러도 새 창이 안 뜨고 하얀 창만 포커스된다(`instance_lock` 이 '이미 실행 중' 판정).
= 사용자가 **재실행으로 빠져나올 수 없는 상태**에 갇힌다. 이게 "안 열린다" 의 정체.

**How to apply:**
- 🔴 **진단 정본 2개**: 설치 런타임 = 레지스트리
  `HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}\pv`,
  UDF 가 묶인 버전 = `webview_data/EBWebView/Last Version` 파일. **둘이 다르면 이 사고다.**
  폴더(`EdgeWebView/Application/<버전>/`)로 판정하면 안 된다 — 옛 버전 폴더가 남아 공존한다
- 🔴 **하얀 화면인데 서버는 멀쩡하다**. 스플래시 배경이 다크(`#1e1e1e`)이므로
  **하얀색 = HTML 자체가 안 실린 것** = 엔진 미부착 신호. 서버/dist 부터 뒤지면 헛수고
- **즉시 복구**: 그 UDF 를 쓰는 `msedgewebview2` 프로세스를 죽이면 락이 풀린다
  (`--user-data-dir` 로 골라낼 것 — 이름만 보고 다 죽이면 윈도우 검색·위젯·구글드라이브까지 죽는다).
  그 다음 하얀 창 프로세스를 닫고 재실행하면 UDF 가 새 버전으로 재봉인된다
- 🔴 **앱이 관리자 권한으로 떠 있으면 일반 권한 셸에서 못 죽인다**. `taskkill` 은 Access denied,
  `PostMessage(WM_CLOSE)` 는 UIPI 에 막혀 False. 사용자가 직접 X 버튼/작업 관리자를 써야 한다
- **재발 방지 코드**: `infra/webview_health.py` 가 스플래시 로드를 감시해 실패 시 진단문을
  MessageBox 로 띄우고 **락을 놓고 종료**한다. 자동으로 남의 프로세스를 죽이지는 않는다 —
  '좀비' 와 '정상 사용 중' 을 확실히 못 가르면 멀쩡한 창을 하얗게 만든다

#### 사고 ③ 🔴🔴 자책 — 감시가 부팅을 멈췄다 (2026-08-15, 4fde303 → 8596fc5)

사고 ②를 고치려고 넣은 감시 코드가 **부팅 자체를 정지**시켰다. 증상은 하얀 창이 아니라
**창 '응답 없음'**(`Responding=False`)이라 원인이 더 안 보였다.

**Why:** 감시가 `BrowserView.instances → browser.webview.CoreWebView2` 를 0.2초마다 폴링했다.
🔴 **WebView2 는 WinForms 컨트롤이고 창을 만든 STA 스레드 전용이다.** 게터를 다른 스레드에서
읽으면 UI 스레드 동기화가 필요한데, 그 STA 스레드는 마침 스플래시를 그리는 중
(`NavigateToString`)이었다 → 상호 대기 → STA 메시지 루프 정지 → `loaded` 이벤트 미발생 →
`_update_splash` 의 `evaluate_js` 무한 대기 → **부팅 전체 정지**.

**How to apply:**
- 🔴 **pywebview 창의 생존을 볼 땐 `window.events.loaded` 만 본다.** 순수 threading.Event 라
  크로스스레드 안전하고, '엔진이 붙어 페이지가 실제로 떴는가' 를 CoreWebView2 존재 여부보다
  정확히 답한다. `evaluate_js`/`CoreWebView2` 등 WebView2 를 타는 건 감시에 쓰지 말 것
- 🔴 같은 폴링이 `webview_permissions._find_core` 에도 있다. 지금은 Microsoft 바인딩이 있을
  때만 도달해 부팅 임계 구간을 비껴가지만, **호출 시점을 앞당기면 같은 교착이 난다**
- 🔴 **진단 정본은 py-spy 스택**이다. `pip install py-spy` → `py-spy dump --pid <PID>`.
  `_update_splash → evaluate_js → wait(event.py)` + `load_html(edgechromium.py:208)` 조합이
  이 교착의 지문. 로그로는 `Launching Desktop Window` 에서 멈춘 것만 보여 원인을 못 가른다
- 🔴 **범인 확정법은 커밋 되돌리기**: `git checkout HEAD~1 -- <파일>` 로 직전 커밋만 되돌려
  재기동. 여기서 정상이면 내 수정이 원인이다. 재현 스크립트가 전부 통과하는데 앱만 죽으면
  **재현 조건이 앱과 다른 것** — 이 경우 차이는 '감시 코드 유무' 하나였다

### 모듈 상단 `[제약]`

앱 서버(server.py)가 /api/voice/* 를 이쪽으로 프록시한다.
[🔴 왜 앱과 같은 프로세스가 아닌가 — 이 구조의 존재 이유]
음성 스택은 python 3.10 + torch(CUDA) 를 요구한다. 앱 venv 는 3.12/3.13 에
가벼운 의존성으로 서 있다. 한 환경에 섞으면
① torch 버전 핀이 앱 의존성과 충돌하고
② 모델 로딩(수십 초, GPU 수 GB)이 앱 기동을 붙잡고
③ 음성 라이브러리가 죽을 때 대시보드까지 같이 죽는다.
프로세스를 가르면 셋 다 사라진다. node PTY 서버를 따로 띄우는 것과 같은 판단.
[🔴 모델은 첫 요청 때 올린다] 기동만으로 GPU 를 물면, 음성을 안 쓰는 사람도
VRAM 을 뺏긴다. 대신 /status 가 loading 을 알려 화면이 '준비 중'을 그린다.
[제약] 이 파일은 **음성 venv** 에서 돈다. 앱 패키지(ai_monitor.*)를 import 하지
말 것 — 그 순간 두 환경이 다시 묶인다. 표준 라이브러리와 음성 라이브러리만.
