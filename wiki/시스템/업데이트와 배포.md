### 🧠 feedback_spec_datas_check

**PyInstaller 번들에 들어갈 새 디렉토리/파일 추가 시 `vibe-coding.spec` datas + `.github/workflows/build-release.yml`의 `--add-data` 양쪽을 함께 갱신. 한쪽만 고치면 frozen EXE에서 ModuleNotFoundError·버전 미표시·자동 업데이트 마비**

PyInstaller 번들에 새 디렉토리/파일을 추가할 때는 **두 곳 모두** 갱신해야 한다:

1. `vibe-coding.spec` → `datas=[...]`에 `('.ai_monitor/<폴더>', '<폴더>')` 또는 `('.ai_monitor/<파일>', '.')`
2. `.github/workflows/build-release.yml` → 두 pyinstaller 명령(noconsole + console) 양쪽에 `--add-data "<폴더>;<폴더>"` 또는 `--add-data "<파일>;."` 추가

**Why:** CI는 spec 파일을 사용하지 않고 `pyinstaller --onefile ... server.py` 형태로 명령줄 인자만으로 빌드한다. spec datas만 갱신하면 로컬 `pyinstaller vibe-coding.spec`은 통과해도 CI에서 만든 설치 EXE는 해당 파일이 누락된 채로 배포된다.

같은 패턴이 이미 두 번 터졌다:
- v3.7.215~218 — `.ai_monitor/infra/` 디렉토리 분리 누락 → ModuleNotFoundError로 부팅 실패 + 자동 업데이트 마비, 4개 릴리즈 좀비 배포
- v3.7.207~223 — `_version.py` 파일 추가 누락 → server.py가 frozen 모드에서 파일 읽기 실패 → `__version__ = "0.0.0-unknown"` → UI 우상단 버전 미표시 (사용자가 여러 번 지적했는데 못 잡음)

루트 원인은 **server.py가 _version.py를 import에서 파일 읽기로 바꾼 시점에 CI command의 `--hidden-import _version`이 무용해졌다는 사실을 spec만 보고는 알 수 없다**는 점. spec datas와 CI args가 따로 관리되니 디버깅이 spec에서 멈춘다.

**How to apply:**
- `.ai_monitor/` 아래에 새 디렉토리/파일 추가 PR이라면 자동으로 spec **그리고** build-release.yml 양쪽 diff를 만든다.
- 모듈 분리·이동 시 grep으로 `from <폴더>.` 또는 파일 직접 참조(`open(...)`, `_MEIPASS`)를 먼저 파악하고, 그 경로가 CI args에도 명시돼 있는지 확인한다.
- `import X` → `open('X.py')` 같은 로딩 방식 변경은 `--hidden-import`가 아닌 `--add-data`가 필요해진 신호로 본다.
- `/vibe-release` Step 0.5(로컬 EXE smoke test)를 건너뛰지 않는다 — 두 사고 모두 smoke test로 잡혔을 사고.
- 이상적으로는 CI를 `pyinstaller vibe-coding.spec`로 통일해 단일 진실 원천으로 만드는 게 근본 해결책. 분리 상태가 유지되는 한 이 메모리 유지.

### 🧠 project_claude_update_lock

**Claude Code 자동 업데이트가 \"success\"인데 옛 버전 — 바이브 코딩이 claude.exe 잠금. rename 트릭으로 해결**

바이브 코딩 환경에서 Claude Code(네이티브 설치) 자동 업데이트가 계속 옛 버전으로 뜨는 재발 패턴.

**증상:** `claude --version`이 옛 버전인데 `~/.claude/.last-update-result.json`은 `"outcome":"success"`. 새 버전은 `~/.local/share/claude/versions/<ver>`에 다운로드돼 있으나 런처 `~/.local/bin/claude.exe`만 옛 버전 그대로(해시 비교로 확인 가능).

**근본 원인 (Why):** 바이브 코딩 앱(PyWebView + Node PTY 서버)이 `claude.exe`를 자식 프로세스로 상시 띄워둠 → 표준 업데이터의 *덮어쓰기* 방식이 파일 잠금(lock)에 막혀 런처 스왑만 매번 실패. OS 터미널 창을 닫아도 앱이 프로세스를 살려두므로 락이 안 풀림. **업데이트마다 재발 가능.**

### 업데이트 후 "Failed to load Python DLL" 부팅 실패 (2026-07-07 발생, v3.7.244)

#### 증상
설치본에서 업데이트 버튼 → 새 EXE 부팅 시 두 에러:
1. `Failed to load Python DLL 'C:\Users\...\AppData\Roaming\VibeCoding\runtime\_MEI<...>\python311.dll'. LoadLibrary: 지정된 모듈을 찾을 수 없습니다`
2. `Failed to remove temporary directory ...\_MEI<...>`
→ 앱 실행 불가.

#### 근본 원인 (진단 사슬)
- 깨진 `_MEI` 폴더엔 `pty-server`만 있고 **python311.dll·base_library.zip 누락** = onefile 추출이 극초반 중단.

- 좀비 발생 원인: `updater.py apply_update_from_temp`의 **`os._exit(0)`가 atexit 정리(cleanup_child_procs/cleanup_pyinstaller_temp)를 전부 건너뜀** → 이전 인스턴스 node PTY 서버가 안 죽고 좀비화.
- **onefile 부트로더는 Python 코드보다 먼저 python DLL을 로드** → 앱 내부 정리 로직으로는 원천적으로 못 막음. '교체되는 이전 프로세스'가 새 EXE 기동 전에 정리해야 함.
- 악화 요인: `runtime_tmpdir='%APPDATA%\VibeCoding\runtime'` **고정**(2026-03-16, 백신 회피용) → 좀비가 잠근 잔여 _MEI와 새 부팅이 충돌.

#### 수정 (v3.7.245, 커밋 9c2030b)
- `infra/pty_process.py` **`kill_runtime_mei_orphans(runtime_dir, exclude_mei, only_orphans)`** 신규:
  runtime 하위 _MEI node만 ExecutablePath 필터로 정밀 종료(dev/글로벌 node 불건드림).
  `only_orphans=True`면 부모(vibe-coding.exe) 생존 판정으로 **살아있는 다른 인스턴스 보호**([[작업 방식 결정]] 아닌 정밀 수정, v3.7.122 무차별 kill 재발 방지).
- `updater.py`: `os._exit(0)` **직전** `kill_runtime_mei_orphans(exclude 없음)` 호출 — 핵심.
- `infra/lifecycle.py cleanup_pyinstaller_temp`: rmtree 전 락 좀비(only_orphans=True) 선정리.
